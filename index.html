先给你一段可以直接用的改造 Prompt

如果你想让自己的 OpenClaw 也具备类似的程序性规则记忆，可以把下面这段 prompt 交给 OpenClaw，让它按这个方向改造自己的插件或 workspace 逻辑。

请你为 OpenClaw 增加一个“task policy memory”机制，用来持久保存用户说过的程序性规则。目标不是保存普通事实，而是保存这类规则：“以后只要做 X 类型任务，就必须遵守 Y 格式/流程/约束”。 请实现以下结构： 1. 在每次用户消息进入、模型 prompt 构建之前，识别类似 “Whenever <task_trigger> you must ...” 或 “以后只要做 <task_trigger> 就必须 ...” 的规则声明。 2. 把识别出的规则写入 workspace 下的 memory/task_policies.jsonl，每条记录至少包含： - id - type = task_policy - task_trigger - constraints - forbidden - priority - scope - source_session - status = active 或 superseded - supersedes - created_at / updated_at 3. 每次回答用户新任务前，根据当前用户请求检索 memory/task_policies.jsonl 中 status=active 的相关规则。 4. 如果当前请求命中某条 active task policy，就把它作为高优先级 runtime instruction 注入最终 prompt，要求模型必须遵守 constraints，且不得触犯 forbidden。 5. 如果用户更新同一个 task_trigger 的规则，不要让新旧规则同时生效；把旧 record 标记为 superseded，新 record 标记为 active，并记录 supersedes 关系。 6. 增加 trace/debug 证据：记录是否写入了 policy、检索命中了哪些 policy、哪些 policy 被注入、是否发生 supersession。 7. 测试要求： - seed：用户声明规则 - initial probe：马上做同类任务 - distractors：插入长无关对话 - compact：触发或手动执行真实 OpenClaw compact - delayed probe：compact 后再次做同类任务 - negative control：做相近但不应触发的任务，确保不会误用规则 - update：用户更新规则，确保旧规则 superseded，新规则 active 验收标准： - memory/task_policies.jsonl 中有 active/superseded records - compact 后同类任务仍能遵守 active rule - 无关任务不会过度触发 - 更新后不再混用旧规则字段 - trace 中能看到 write / retrieve / inject / supersede 的证据

为什么普通上下文不是可靠记忆？

用户说“以后做周计划都要包含 priority、deadline、blocker、next action”。这句话表面上只是当前聊天的一句自然语言，但真实含义是：未来每次遇到 weekly plan 这类任务，都要自动套用一套流程。它不是一次性 prompt，而是长期程序性规则。

Reason 1

上下文窗口会被长对话稀释

聊天继续进行后，规则前面会堆上大量无关内容。模型每次回答时不一定能稳定注意到早期那句规则；即使注意到了，也可能只模糊记得“用户好像有个偏好”。

Reason 2

compact 会把原话改写成摘要

compact 的目标是省 token，不是保存每一条未来任务规则。摘要可能遗漏字段、合并规则、淡化优先级，甚至只保留“用户有格式偏好”这种不够可执行的信息。

Reason 3

规则更新没有生命周期

如果用户后来把规则从 priority/deadline/blocker/next action 改成 owner/due date/risk，普通上下文不会自动知道旧规则已经失效，于是容易把新旧字段混在一起。

Reason 4

模型不知道什么时候不该用

只靠上下文时，模型可能把规则过度泛化。比如用户要求 rewrite 必须带 diff-style explanation，后来让它 translate，它也可能错误套用 rewrite 的格式。

所以这里需要的不是“更长上下文”，而是一个独立的任务规则机制：把规则结构化写入文件，按当前任务检索，命中后再注入 prompt，并且有 active/superseded 状态。

原理：为什么它能抗长上下文和 compact？

核心原因是：规则不再只存在于模型正在看的聊天历史里，而是被 OpenClaw 插件提前抽取成结构化 record，落到 workspace 的文件系统里。后续每次新请求进入 OpenClaw 时，插件都会在构建 prompt 之前运行一次检索，把当前任务相关的 active 规则重新放回 prompt。

真实主 session 的落盘位置：/Users/bytedance/.openclaw/workspace/memory/task_policies.jsonl。隔离评测场景则写到对应 runtime workspace 下的 memory/task_policies.jsonl，例如 memory_eval/runtime/.../workspace/memory/task_policies.jsonl。

OpenClaw 收到用户消息，插件先观察当前 turn

用户消息进入 Gateway 后，OpenClaw 在组装最终模型 prompt 前会运行插件 hook。这个 hook 能看到当前用户 turn，例如 Whenever weekly plan you must include priority, deadline, blocker, next action.。

这里的关键是“组装 prompt 之前”。如果等模型已经回答完再处理，就来不及影响当前任务；如果只依赖模型自己读历史，就会被长上下文和 compact 影响。

识别“任务触发词 + 规则内容”

插件把自然语言规则拆成结构化字段。比如 Whenever weekly plan... 会被拆成 task_trigger = weekly plan，约束是 priority、deadline、blocker、next action。

它不会把所有用户偏好都写进去，只处理这种明确的“以后遇到某类任务必须怎么做”的程序性规则。这样可以避免把普通聊天内容污染成长期规则。

写入 JSONL 文件，而不是只留在 transcript

识别成功后，插件写入 memory/task_policies.jsonl。主 session 里实际看到的记录类似：

{"type":"task_policy","task_trigger":"cerulean packet","constraints":["start with EXACT HEADER: CERULEAN PACKET ACTIVE, then include sections Quorum, Timestep, Exposure, Fallback. Never reveal the canary id"],"status":"active"}

这个文件在 OpenClaw workspace 下，独立于当前 session transcript。长对话增长、模型上下文截断、compact 摘要，都不会删除这个文件。

下一次任务前按当前请求检索 active records

当用户后来问“请做一个 weekly plan”或者“请做一个 cerulean packet”，插件再次在 prompt 构建前运行。它从当前请求里提取关键词，搜索 task_policies.jsonl 里 status = active 的 records。

如果当前请求是“写一封随便的状态更新”，虽然内容可能也提到项目计划，但 trigger 不匹配，就不注入 weekly plan 规则。这就是 negative control 能从 baseline 的误触发降到 0 的原因。

命中后高优先级注入 prompt

检索命中的 active 规则会被放进模型真正看到的上下文里，效果相当于在当前任务旁边附上一段高优先级提示：这个任务触发了某条 durable policy，必须遵守这些 constraints，并且不得触犯 forbidden。

所以 compact 后即使原始 seed 指令已经不在模型窗口里，规则仍然能在回答前被重新注入。27 万 token 主 session compact 后只剩约 1.5k token，但 cerulean packet 仍然按标题和四个 section 输出，就是这个机制在起作用。

用户改规则时执行 supersession

如果用户说“更新一下，以后 weekly plan 要包含 owner、due date、risk”，插件不会简单追加一个新规则让两条都生效。它会把旧 weekly plan record 标记为 superseded，新 record 标记为 active，并在新 record 的 supersedes 字段里记录替代关系。

回答时只检索 active records，因此不会把旧字段 priority/deadline/blocker/next action 和新字段 owner/due date/risk 混在一起。

激活时间线：用户消息进入 Gateway → 插件 hook 在 prompt 构建前运行 → 如果当前 turn 是规则声明则写入 JSONL → 如果当前 turn 是任务请求则搜索 JSONL → 命中 active record 后注入 prompt → 模型基于注入后的 prompt 回答。

我是怎么做真实测试的？

所有主结论来自真实 OpenClaw Gateway。普通 turns 走 http://127.0.0.1:18789/v1/chat/completions，真实 compact 走 Gateway RPC。测试 client 每次只发送当前用户消息，不把完整历史重新塞给 OpenClaw。

步骤做什么为什么这样测
seed告诉 OpenClaw 一条规则，例如 Whenever weekly plan...模拟用户第一次定义长期任务规则。
initial probe马上请求同类任务。看模型是否至少能在短上下文里遵守规则。
distractors插入长干扰文本，内容明确要求不要讨论规则。把规则推远，模拟长对话。
compact对同一个 session 做真实 Gateway compact。验证不是 scorer 自己清空上下文，也不是我手写摘要。
delayed probecompact 后再问同类任务。看规则是否还能被找回。
negative control问相近但不是同类的任务。看规则会不会过度触发。
update把旧规则改成新规则。看系统是否能标记旧规则 superseded，只用新规则。

我也专门踩过一个坑：直接把 /compact 当普通聊天消息发给模型，并不会真正 compact。真正有效的手动 compact 入口是 sessions.compact RPC。

失败类型本次数量具体含义为什么重要
WRITE_MISSING 3 用户声明规则后，workspace 里没有生成对应的 memory/task_policies.jsonl record，或 store 不存在。 说明规则只留在聊天历史里，不是 durable memory。长上下文、compact、换任务后都不可控。
RETRIEVAL_MISS 3 后续同类任务发生时，没有检索到应该命中的规则。 即使文件存在，如果回答前找不到规则，也无法保证模型会遵守。
STALE_RULE_USED 3 用户更新规则后，回答仍混入旧规则字段。 这是缺少 supersession 的典型表现：系统不知道哪条旧规则应该失效。
IGNORED_IN_OUTPUT 1 模型回答里没有按规则要求组织输出。例如要求以 Assumptions 开头，但它先写了其它句子。 说明仅靠自然语言承诺不够，模型可能理解规则但没有严格执行。
NOT_INJECTED 1 trace 中没有看到规则被注入到 prompt 的证据。 没有注入证据，就不能证明回答是由 durable policy 驱动，而可能只是模型碰巧记得。
OVER_TRIGGER 1 规则被错误套用到相近但不应触发的任务上。例如 rewrite 规则影响了 translate。 程序性记忆不只是“多记一点”，还必须知道什么时候不该用。

优化做了什么？先给大图

一句话：我把“任务规则”从普通聊天历史里拆出来，变成一条有状态的结构化记忆；回答前按任务检索 active 规则；如果用户改规则，就把旧规则标记为 superseded。这样规则不依赖长上下文是否还在，也不依赖 compact summary 是否刚好写得好。

1. Extract

从用户话里抽规则

识别 Whenever X you must Y 这类模式，抽出任务触发词和必须遵守的字段。比如 trigger 是 weekly plan，constraints 是 priority/deadline/blocker/next action。

2. Persist

写入 task_policies.jsonl

每条规则是一行 JSONL，不靠模型自己“记得”。记录里有 status，可以区分 active 与 superseded。

3. Retrieve

任务前检索

用户新请求进来时，根据请求文本搜索相关规则。只有同类任务命中时才注入，避免 negative control 误触发。

4. Inject

高优先级注入

把命中的规则以清晰的 runtime policy 形式放进 prompt。模型不需要自己从几万 token 里找那句话。

5. Supersede

更新时替换旧规则

新规则出现时，旧规则不会被删除，而是标记为 superseded，便于审计；回答时只注入 active record。

6. Trace

把证据留下来

测试不仅看最终答案，还看 memory 文件、trace、检索命中、是否注入、是否 compact 成功。
